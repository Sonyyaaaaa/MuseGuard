# Порівняння MuseGuard без ОС і з FreeRTOS

Підсумок від 15.11.2026: виміряні результати та межі наведено нижче. FR-13 не виконана повністю; reset, ORE та енергоспоживання мають окремі межі доказів. Прочерки не є нулями або успішними перевірками. Джерела та методи у [rtos-design.md](rtos-design.md), [baseline-lab4.md](baseline-lab4.md) і нижче.

## Умови

Контролер C031C6, 48 МГц, UART 115200, STM32 HAL, Ubuntu 24.04, Docker, Wokwi. Для порівняльного link обидві версії зібрано однаковими прапорцями: `-Os`, а `Platform/platform.c` — `-Og`. Причина такого вибору: у короткому пробному запуску ЛР3 з `-Os` для всіх файлів повторювалися I²C timeout, а пробний `-Og` для файлу платформи їх не показав; конкретну першопричину не встановлено. RTOS link із суцільним `-Og` перевищив code region на 1532 B. Однакові прапорці не означають тотожність машинного коду чи функцій двох версій. Карти цих link: [bare](metrics/lab4/bare-mixed.map), [RTOS](metrics/lab4/rtos-mixed.map). Парний S2 цих ELF виконано 08.11.2026.

SHA-256 порівняльних ELF: ЛР3 `f6c7995acea914391cf02d18b7299953a3e5b01d6b7282f48c73ec4aa71ef4ea`, ЛР4 `ea0b2d79cbef504014e5bba4b70fdfa6b6061507f528a24c0a8b060cc6b33044`. Це ідентифікатори парних виміряних образів, включно з S2 від 08.11; ранній окремий S2 від 04.11 використовував інший RTOS ELF.

Кожне число пам'яті — результат link обраного ELF, не вимір фактичного максимально можливого використання RAM. Журнал зберігає дві 2-KiB сторінки поза code region. У `.bss` RTOS вже є масив heap 6144 B, у якому розміщуються стеки 1536+2560+512=4608 B, TCB, mutex і allocator overhead: повторно додавати ці складові до RAM не можна. Статичне кільце подій має 16×12=192 B плюс індекси; 2 FreeRTOS mutex реалізовані через об'єкти ядра, окремих FreeRTOS message queues у продукті немає. MSP reserve 2048 B і C heap reserve 512 B враховані linker; runtime high-water не є гарантією всіх шляхів.

Прямий внесок секцій об'єктів ядра за RTOS map (байти Flash/RAM): `tasks.o` 2465/196, `list.o` 106/0, `queue.o` 1114/0, `port.o` 428/4, `heap_4.o` 472/6172, `timers.o` 0/0; додатково `rtos_app.o` 1010/84. У 6172 B вже входить масив heap 6144 B. Це сума розміщених вхідних секцій за їхніми адресами, без shared libc і linker padding; RAM-адресовані ініціалізовані дані тут не приписані до Flash. Тому сума не є загальним приростом між версіями. [Машинний аналіз map](metrics/lab4/kernel-map-analysis.json).

## Інші виміряні дані, не парне порівняння ЛР3/ЛР4

- S2 FreeRTOS, інший ELF із `-Os` для всіх файлів: від `z` до фінального `s` 3600555 мс MCU, 180027 releases, skipped=0, finish_miss=0, release_max=14000 мкс. Дані UART і 12 PIR: [raw](metrics/lab4/uart.raw), [PIR VCD](metrics/lab4/pir.vcd), [validator](metrics/lab4/independent-validation.json). Збережено 19 послідовних CRC-valid записів. Крок внутрішнього таймера 1 мс; нульовий виміряний jitter не доводить відсутність субмілісекундного jitter.
- Під час двох спроб S2 ЛР3 04.11 collector завершився через 60 с без UART після 314007 і 119007 мс MCU. Ще одна спроба 08.11 перервалася на 3575009 мс. Фрагменти не сумуються і не входять до успішної пари; першопричина зупинок не встановлена.
- Пілот ОС, окремий ELF: 22 пари ISR-marker→event-marker по 68,75 мкс у Wokwi, результат включає ISR, планувальник і GPIO, не є ізольованою вартістю перемикання. [VCD](captures/lab4/pilot-wokwi.vcd), [аналіз](metrics/lab4/pilot-analysis.json). Це не ISR→task час продукту і не повна хронологія S3.
- Контрольоване порівняння двох діагностичних меж I²C timeout у ЛР4: однакові 550 байтів UART, 50 PIR, SDA low 25–30 с. Максимум маркера state mutex під час fault: 22,004 → 17,015 мс; recovery після release SDA ≈2,030 с, наступний read status=0, ID=104. У кожному dump 109 CRC-valid рядків, 57 унікальних sequence. Це порівняння двох варіантів ЛР4, не ЛР3 проти ЛР4. [Аналіз](metrics/lab4/compare-analysis.json), [UART до](metrics/lab4/compare-wide.uart.txt), [UART після](metrics/lab4/compare-short.uart.txt). Сигнал PA9 не охоплює невеликі інтервали між API та GPIO і не встановлює гарантований WCET.
- Додатковий аналіз тих самих VCD за 25–30 с: по 250 повних імпульсів SAMPLE у кожному run. Найбільша ширина маркера 21,952 мс до і 16,951 мс після; найбільший інтервал між початками 22,097 і 22,642 мс, по 6 із 249 інтервалів довші за 20 мс. Ширина GPIO не включає час до початку задачі, а інтервал між її початками не є самостійним виміром deadline від release. PIR-фронтів під час fault у сценарії не було, отже реакцію PIR під fault не перевірено; маркер також не доводить коректність ADC. [Числа та SHA-256 вихідних VCD](metrics/lab4/fault-sample-analysis.json). У snapshots до/після fault сукупний `finish_miss` зріс з 1 до 2 в обох варіантах; потрібні додаткові дані для встановлення часу й причини кожного miss.
- Host tests для обох версій проходять включно з моделлю CRC, rollover і byte-cut. Host-модель не перевіряє поведінку внутрішньої flash моделі MCU під час обриву запису.

## Окремі досліди ядра

Це окремі діагностичні ELF на основі пілота, а не випробування кільця чи стеків повного продукту. В одному запуску інверсії high task чекала 80 ticks із mutex та 205 із binary semaphore, зовнішні GPIO дали 80,050825/205,091225 мс при tick 1 мс. При 1024 B kernel heap спрацював malloc-failed hook і пілот зупинився. Черга на 4 записи за 20 неблокувальних відправок прийняла 4, відхилила 16; споживач отримав 4. Зі стеком periodic 32 слова контроль overflow спрацював; без нього UART продовжився із watermark 0 і лічильником подій, що перестав зростати. Активне очікування високої задачі зупинило прогрес low та idle до її блокування; це лічильники прогресу, не CPU runtime stats. [Результати, GPIO і SHA-256](metrics/lab4/rtos-experiments.json), повні збірки і VCD — у Lab04/Work/experiments-7.2.

Окремий S3 з 100 Гц порівняно з 1000 Гц: ідентичність 2015 UART байтів та 30 PIR перевірена за VCD (≤25 нс), у кожному 30/30 PRESENCE і 0 skipped/finish miss. SAMPLE період за VCD: 19,752–20,231 / 19,789–20,179 мс; max command latency у burst 1030/1390 мс. Для 100 Гц окремо адаптовано HAL timebase до кроку 10 мс та мінімальне блокування service з 1 до 10 мс; це змінює поведінку поза частотою kernel tick. Вбудована оцінка sample duration має недостатню роздільність і в цьому run дорівнює нулю. `busy_permille` 219/87 не є оцінкою idle або overhead; окремі GPIO та TIM3/trace результати наведено нижче. [Аналіз двох VCD](metrics/lab4/tick-s3-analysis.json), [UART 100 Гц](metrics/lab4/tick100.uart.raw).

Діагностична пара 08.11 з GPIO-маркерами на тому самому генераторі S3: sensor/service/idle high 11,915/25,519/62,525% при 1000 Гц і 11,905/12,689/75,400% при 100 Гц. SysTick ISR (HAL + ядро) high 3,268/0,672%, інтервал між trace hooks планувальника 2,837/0,403%; ці частки перекриваються. Маркери додають витрати і не відділяють усі IRQ від часу задач; 100 Гц також змінює HAL timebase і затримку service. Повна вартість context switch не виміряна. У 1000 Гц 1444 переходи service→sensor, 1335 під час COMMAND high; маркери не визначають причину готовності. ELF, VCD і аналіз — Lab04/Work/trace-20261108/RESULT.md та trace100-20261108/analysis.json.

Збереження журналу через reset та обрив запису має конкретне обмеження моделі; FR-13 має виміряні порушення. Чинні статуси наведено нижче. Відмінність порту від прикладу: CM4F замінено на GCC/ARM_CM0 для C031.

## Попередні конкретні досліди 08.11

Наступні записи фіксують результати й межі окремих ранніх дослідів; чинне зведення враховує додаткові перевірки 15.11 вище.

Окремий короткий RTOS-тест 08.11: SHOCK, TILT і LIGHT та `k` записано до журналу; підтверджено CRC усіх 14 рядків двох dump для 8 унікальних номерів. Перед налаштуванням нахилу модель ставили на паузу, перший collector завершився за таймаутом, а подію TILT незалежно відновлено з UART у VCD та пізнішого журналу. LIGHT зафіксовано другим UART після заповнення VCD-буфера, без незалежної VCD-перевірки. [Аналіз і хеші](metrics/lab4/fr-sensor-20261108.json), [перший UART](metrics/lab4/fr-sensor-first-20261108.uart.raw), [другий UART](metrics/lab4/fr-sensor-second-20261108.uart.raw); повний VCD — Lab04/Work/fr-sensor-20261108/RESULT.md.

Короткий сценарій команд 08.11 на тому самому RTOS ELF: дві `a` залишили ACCESS, `g` повернула GUARD; 10 команд мали різницю міток RX→CMD 1–7 мс при кроці таймера 1 мс. У трьох dump всі 14 рядків CRC-valid (5 унікальних записів). Статистика містить один skipped і один finish miss, момент і причина не встановлені. Після повного Restart симуляції старі записи 4–5 не з'явилися, BOOT показав seq=0/corrupt=128; через невідомий стан моделі flash це не ізольований reset МК і не доводить причину втрати. Power-cut і відновлення після reset не підтверджені в моделі; це обмеження FR-09/12, описане нижче. Сирі журнали та межі — Lab04/Work/fr-combined-20261108/RESULT.md.

У наступному запуску на тому самому ELF повторна `a` не продовжила 60 с від першої; TILT в ACCESS зберігся без alarm, після автоматичного GUARD той самий нахил через 520 мс спричинив alarm і LED high. CRC підтверджено для 11 рядків/7 записів. Під час установки вектора симуляцію ставили на паузу; прямого latency до LED не заявлено. Lab04/Work/access-tilt-20261108/RESULT.md.

Окремий діагностичний ELF повторно відкрив поточну flash без reset: seq=4, valid=4, corrupt=124. Після штучної помилки program наступні дві події не записалися, flash_fail=2, попередні записи лишилися. У іншій діагностичній збірці вибрані слова невикористаних слотів 0 та 68 були нульовими, а не FF; тому лічильник corrupt не означає 124 доведено пошкоджені записи. Причину стану flash (модель або взаємодія з драйвером) не встановлено. Lab04/Work/flash-diagnostic-20261108/RESULT.md.

Окрема перевірка повного 32-KiB HEX із початковою областю журналу FF дала `corrupt=0` та slots 0–3: початковий образ визначає цей прояв у Wokwi. Програмний SYSRESETREQ не привів до нового BOOT у спостережуваному вікні. Це не підтверджує збереження через reset. Lab04/Work/reset-filled-20261108/RESULT.md. Номінальний потік 36 команд `n` на парному ELF: RX-інтервали 1958–2076 мс, max ISR RX→обробка 8 мс за таймером 1 мс; накопичені skipped/finish miss по одному. Lab04/Work/nominal-uart-20261108/RESULT.md.

## Підсумок 15.11.2026

Продуктовий ELF `ea0b2d79cbef504014e5bba4b70fdfa6b6061507f528a24c0a8b060cc6b33044` збережено. Парні S1/S3 від 04.11 і S2 від 08.11 належать тим самим виміряним образам. Додаткові діагностичні ELF не підміняють їх.

На продуктовому ELF 15.11: 30/30 SHOCK тривалістю 20 мс, LED max 20,631525 мс; 60/60 заданих масок PRESENCE/LIGHT/SHOCK в обох режимах; 60/60 TILT через 505 мс, зі збереженням попередньої тривоги в ACCESS. У фінальному dump 128/128 CRC. За вікно отримано 7949 опитувань без skipped, finish_miss та event_drop. Номінальні 60 команд із періодом 1 с мали максимум 6 мс; 3499 опитувань і 93/93 CRC. Всі UART-рядки незалежно відновлені з native VCD.

Host-тест реального кільця runner: 30 повторень, 16 із 24 подій прийнято, 8 відхилено з лічильником, FIFO після читання й повторного заповнення збережено; 600 CRC-коректних записів. Політика перевірена у 30 host-сценаріях зі зсувом через wrap: ACK зберігає tilt latch та еталон, ACCESS завершується через перші 60000 мс. Це окремий рівень доказів.
