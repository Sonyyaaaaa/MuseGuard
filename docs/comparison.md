# Порівняння MuseGuard без ОС і з FreeRTOS

Стан: проміжне порівняння, не готова ЛР4. Центральна таблиця містить лише отримані результати; прочерки не є нулями або успішними перевірками. Джерела та методи у [rtos-design.md](rtos-design.md), [baseline-lab4.md](baseline-lab4.md) і нижче.

## Умови

Контролер C031C6, 48 МГц, UART 115200, STM32 HAL, Ubuntu 24.04, Docker, Wokwi. Для порівняльного link обидві версії зібрано однаковими прапорцями: `-Os`, а `Platform/platform.c` — `-Og`; тег `lab3` збережено. Причина такого вибору: у короткому пробному запуску ЛР3 з `-Os` для всіх файлів повторювалися I²C timeout, а пробний `-Og` для файлу платформи їх не показав; конкретну першопричину не встановлено. RTOS link із суцільним `-Og` перевищив code region на 1532 B. Однакові прапорці не означають тотожність машинного коду чи функцій двох версій. Карти цих link: [bare](metrics/lab4/bare-mixed.map), [RTOS](metrics/lab4/rtos-mixed.map). Парний S2 для цих ELF ще не виміряно.

SHA-256 порівняльних ELF: ЛР3 `f6c7995acea914391cf02d18b7299953a3e5b01d6b7282f48c73ec4aa71ef4ea`, ЛР4 `ea0b2d79cbef504014e5bba4b70fdfa6b6061507f528a24c0a8b060cc6b33044`. Це ідентифікатори збірок для таблиці пам'яті, а не ELF попереднього S2.

Кожне число пам'яті — результат link обраного ELF, не вимір фактичного максимально можливого використання RAM. Журнал зберігає дві 2-KiB сторінки поза code region. У `.bss` RTOS вже є масив heap 6144 B, у якому розміщуються стеки 1536+2560+512=4608 B, TCB, mutex і allocator overhead: повторно додавати ці складові до RAM не можна. Статичне кільце подій має 16×12=192 B плюс індекси; 2 FreeRTOS mutex реалізовані через об'єкти ядра, окремих FreeRTOS message queues у продукті немає. MSP reserve 2048 B і C heap reserve 512 B враховані linker; runtime high-water не є гарантією всіх шляхів.

Прямий внесок секцій об'єктів ядра за RTOS map (байти Flash/RAM): `tasks.o` 2465/196, `list.o` 106/0, `queue.o` 1114/0, `port.o` 428/4, `heap_4.o` 472/6172, `timers.o` 0/0; додатково `rtos_app.o` 1010/84. У 6172 B вже входить масив heap 6144 B. Це сума розміщених вхідних секцій за їхніми адресами, без shared libc і linker padding; RAM-адресовані ініціалізовані дані тут не приписані до Flash. Тому сума не є загальним приростом між версіями. [Машинний аналіз map](metrics/lab4/kernel-map-analysis.json).

Парний S1 04.11.2026: одна схема і тихі сенсорні входи, `z` після прогріву і `s` через 77,007/77,008 с МК. Обидва VCD підтвердили кількість SAMPLE, максимальна ширина 2220,475/2217,725 мкс, firmware release_max 6/10 мс із кроком 1 мс. У RTOS boot був короткий fault/recovery IMU до `z`. Лог RTOS collector не охопив BOOT, але він декодований з UART_TX у повному VCD. [Машинний аналіз](metrics/lab4/s1-analysis.json), [UART ЛР3](metrics/lab4/s1-bare.uart.raw), [UART ЛР4](metrics/lab4/s1-rtos.uart.raw); повні VCD і скрипти — у локальному Lab04/Work/s1-pair-vscode. Це не замінює S3 і не доводить надійної роботи у фоні.

Парний S3 04.11.2026: по 30 пакетів `ag` + 64 `n` + LF, у трьох ще `d`, і 30 PIR high 1 с під навантаженням. Відтворюваний розклад генератора дещо відрізняється від ручного розкладу початкової ЛР3; обидві нові прошивки отримали однакові 2015 байтів та 30 PIR із різницею фронтів не більше 25 нс. Команди `z` і `s` задані через 2 та 250 с. У ЛР3/ЛР4 відповідно 26/24 PIR-фронтів припали на COMMAND high; обидві мали 30 PRESENCE. У кожному run 106 рядків dump пройшли CRC-перевірку, 64 унікальні sequence; це не перевірка вимкнення живлення. [Аналіз](metrics/lab4/s3-analysis.json), [UART ЛР3](metrics/lab4/s3-bare.uart.raw), [UART ЛР4](metrics/lab4/s3-rtos.uart.raw); повні VCD, ELF identity і скрипти — у локальному Lab04/Work/s3-pair-vscode/RESULT.md. Модельні виміри не доводять фізичного WCET.

Парний P20: 400 pulse high 20 мс, 4 групи по 100, у третій 12 пакетів 64 `n`. Однаковість RX і PIR фронтів у двох run підтверджена з точністю до 25 нс; кожна група охоплює всі 20 фазових bins. ЛР3 зафіксувала 299/300 у спокої та 93/100 під burst, ЛР4 300/300 і 100/100. Макс. PIR→UART EVENT під burst 34,485/36,007 мс серед отриманих; у ЛР4 за весь P20 один `finish_miss`, незважаючи на 400 подій. В обох CRC коректна для 128 унікальних записів dump. [Аналіз і входи](metrics/lab4/p20-comparison.json), [UART ЛР3](metrics/lab4/p20-bare.uart.raw), [UART ЛР4](metrics/lab4/p20-rtos.uart.raw); full VCD та сценарій — Lab04/Work/p20-pair-vscode/RESULT.md.

## Інші виміряні дані, не парне порівняння ЛР3/ЛР4

- S2 FreeRTOS, інший ELF із `-Os` для всіх файлів: від `z` до фінального `s` 3600555 мс MCU, 180027 releases, skipped=0, finish_miss=0, release_max=14000 мкс. Дані UART і 12 PIR: [raw](metrics/lab4/uart.raw), [PIR VCD](metrics/lab4/pir.vcd), [validator](metrics/lab4/independent-validation.json). Збережено 19 послідовних CRC-valid записів. Крок внутрішнього таймера 1 мс; нульовий виміряний jitter не доводить відсутність субмілісекундного jitter.
- Під час двох спроб S2 ЛР3 collector завершився через 60 с без UART після 314007 і 119007 мс MCU. Після повернення до вікна модель і UART поновилися; це доказ принаймні тимчасової зупинки просування моделі, але першопричина у Wokwi/віконній системі не встановлена. Фрагменти не сумуються; парний S2 залишається невиконаним.
- Пілот ОС, окремий ELF: 22 пари ISR-marker→event-marker по 68,75 мкс у Wokwi, результат включає ISR, планувальник і GPIO, не є ізольованою вартістю перемикання та не є фізичним виміром. [VCD](captures/lab4/pilot-wokwi.vcd), [аналіз](metrics/lab4/pilot-analysis.json). Це не ISR→task час продукту і не повна хронологія S3.
- Контрольоване порівняння двох діагностичних меж I²C timeout у ЛР4: однакові 550 байтів UART, 50 PIR, SDA low 25–30 с. Максимум маркера state mutex під час fault: 22,004 → 17,015 мс; recovery після release SDA ≈2,030 с, наступний read status=0, ID=104. У кожному dump 109 CRC-valid рядків, 57 унікальних sequence. Це порівняння двох варіантів ЛР4, не ЛР3 проти ЛР4. [Аналіз](metrics/lab4/compare-analysis.json), [UART до](metrics/lab4/compare-wide.uart.txt), [UART після](metrics/lab4/compare-short.uart.txt). Сигнал PA9 не охоплює невеликі інтервали між API та GPIO і не встановлює гарантований WCET.
- Додатковий аналіз тих самих VCD за 25–30 с: по 250 повних імпульсів SAMPLE у кожному run. Найбільша ширина маркера 21,952 мс до і 16,951 мс після; найбільший інтервал між початками 22,097 і 22,642 мс, по 6 із 249 інтервалів довші за 20 мс. Ширина GPIO не включає час до початку задачі, а інтервал між її початками не є самостійним виміром deadline від release. PIR-фронтів під час fault у сценарії не було, отже реакцію PIR під fault не перевірено; маркер також не доводить коректність ADC. [Числа та SHA-256 вихідних VCD](metrics/lab4/fault-sample-analysis.json). У snapshots до/після fault сукупний `finish_miss` зріс з 1 до 2 в обох варіантах; потрібні додаткові дані для встановлення часу й причини кожного miss.
- Host tests для обох версій проходять включно з моделлю CRC, rollover і byte-cut. Host моделювання не підтверджує фізичний power cut або поведінку flash моделі MCU.

## Окремі досліди ядра

Це окремі діагностичні ELF на основі пілота, а не випробування кільця чи стеків повного продукту. В одному запуску інверсії high task чекала 80 ticks із mutex та 205 із binary semaphore, зовнішні GPIO дали 80,050825/205,091225 мс при tick 1 мс. При 1024 B kernel heap спрацював malloc-failed hook і пілот зупинився. Черга на 4 записи за 20 неблокувальних відправок прийняла 4, відхилила 16; споживач отримав 4. Зі стеком periodic 32 слова контроль overflow спрацював; без нього UART продовжився із watermark 0 і лічильником подій, що перестав зростати. Активне очікування високої задачі зупинило прогрес low та idle до її блокування; це лічильники прогресу, не CPU runtime stats. [Результати, GPIO і SHA-256](metrics/lab4/rtos-experiments.json), повні збірки і VCD — у Lab04/Work/experiments-7.2.

Окремий S3 з 100 Гц порівняно з 1000 Гц: ідентичність 2015 UART байтів та 30 PIR перевірена за VCD (≤25 нс), у кожному 30/30 PRESENCE і 0 skipped/finish miss. SAMPLE період за VCD: 19,752–20,231 / 19,789–20,179 мс; max command latency у burst 1030/1390 мс. Для 100 Гц окремо адаптовано HAL timebase до кроку 10 мс та мінімальне блокування service з 1 до 10 мс; це змінює поведінку поза частотою kernel tick. Вбудована оцінка sample duration має недостатню роздільність і в цьому run дорівнює нулю. `busy_permille` 219/87 не є оцінкою idle або overhead, їх ще треба виміряти. [Аналіз двох VCD](metrics/lab4/tick-s3-analysis.json), [UART 100 Гц](metrics/lab4/tick100.uart.raw).

Частина досліду частоти tick щодо CPU idle і витрат ядра, FR-04/05 на поточному RTOS ELF, reset/power-cut у доступному середовищі та повна перевірка FR залишаються невиконаними. Відсутність конкретної перевірки не є дозволеним обмеженням лише тому, що вона описана. Узгодження заміни портового прикладу CM4F на GCC/ARM_CM0 для C031 викладачем не підтверджено.

## Статус функціональних вимог

Це перелік покриття, а не підтвердження всієї вимоги: спостереження з інших ELF не замінюють повторення на парній конфігурації.

| Вимога | Наявні дані та незакриті перевірки |
|---|---|
| FR-01 | У парному S1 є BOOT, UART heartbeat і періодичне опитування; це не перевірка всіх станів запуску. |
| FR-02 | Парний P20: 400/400 PIR у RTOS, 392/400 у суперциклі; це не доводить фізичні властивості PIR. |
| FR-03 | Опитування ADC присутнє; повний RTOS тест порогів освітлення на парному ELF не збережений. |
| FR-04, FR-05 | Окремі впливи shock і tilt на поточному RTOS ELF не підтверджені. |
| FR-06 | У наявних подіях є тип і час; повне покриття всіх типів не встановлено. |
| FR-07, FR-08 | Окремі сенсори працювали, але всі поєднання впливів і правила тривоги на парному RTOS ELF не перевірені. |
| FR-09 | Повний сценарій reset із задокументованим станом на парному ELF не перевірений. |
| FR-10, FR-11 | У парному S3 команди `a` та `g` змінювали режим; усі часові межі, alarm latch і `k` не перевірені. |
| FR-12 | У наявних dump CRC записів коректна; фізичне вимкнення живлення, reset під час запису та повний цикл відновлення не перевірені. Host byte-cut — модель. |
| FR-13 | Парний S3 отримано; RTOS не має finish miss у цьому run, 30 PIR мають UART EVENT ≤31,509 мс. Це не пряме вимірювання LED або усіх типів подій та номінальних команд. |
| FR-14 | Відновлення IMU та втрати RX спостерігалися в парних тестах; flash fault і викликаний hardware overrun у цій парі не перевірені. |

### Граничні пакети UART (парний Wokwi)

Однаковий RX підтверджено VCD (687 байтів, розбіжність фронтів ≤25 нс). Пакети 1/8/32/128/512 команд `n`, між ними `s`: до 128 втрат RX немає, після 512 — 382 в обох версіях; `ore=0`. Накопичувальний максимум затримки для bare/RTOS: 0/1, 99/109, 412/450, 1674/1833, 1680/1841 мс відповідно; `skipped=0`, `finish_miss=0` на фінальному знімку. Вимір стосується лише цієї послідовності. Сирі дані й аналіз у `docs/metrics/lab4/uart-boundary-*`, повні VCD — у Lab04/Work/uart-boundary-pair.

### Watermarks у парних сценаріях

Аналіз RTOS snapshots після S1, S3, P20, SDA fault та пакетного UART на одному ELF: мінімум вільного стеку sensor 262/384 слова (68,23%), service 472/640 (73,75%), idle 116/128 (90,62%); мінімум вільного heap 1080 байт. [Розрахунок та SHA-256 джерел](metrics/lab4/stack-snapshots-analysis.json). Це нижні watermark для виконаних шляхів, не гарантія всіх сценаріїв; MSP та парний S2 залишаються неперевіреними.
